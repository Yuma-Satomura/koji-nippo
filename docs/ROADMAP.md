# 現場管理プラットフォーム化 ロードマップ

工事日報アプリ（koji-nippo）を、現場管理全般を扱うプラットフォームへ段階的に育てるための設計方針書。
2026-10 時点の決定事項をまとめたもの。着手時の指針として使い、方針が変わったら更新する。

---

## 1. 目的と全体方針

- 現状は日報専用。これを **現場管理全般** を担うアプリへ拡張する。
- **このアプリ1つに集約**する（機能ごとにアプリを分けない）。
- **社員ごとにアカウント**を持ち、**役割（管理者／担当者）で権限を分ける**。

> ⚠️ これは「日報アプリへの機能追加」ではなく「**プラットフォームへの作り替え**」。
> 機能を足す前に、認証とマスタの土台を入れ替えるのが成功の鍵。

---

## 2. 現状の整理（2026-10）

| 項目 | 内容 |
|------|------|
| フロント | 素のHTML/CSS/JS（フレームワークなし・ビルドなし） |
| バックエンド | Supabase（会社アカウント `kouzi-nippo` / 東京リージョン） |
| ホスティング | Vercel（会社チーム `oonishi` / Hobbyプラン） |
| 認証 | 管理者PIN 1個（`nippo_settings.admin_pin`）＋ QRの匿名職人 |
| 書き込み | すべて Edge Function 経由（`admin-write` / `worker-write`、service_role） |
| テーブル | `nippo_sites` / `nippo_vendors` / `nippo_reports`(jsonb) / `nippo_settings` |
| 稼働状況 | 本番稼働中（現場「奥長良川」1件・日報51件） |

### 現在の認証モデルの限界

- PINが1個きりで、誰が操作したか記録できない。
- 社員ごと・役割ごとに見える範囲／触れる範囲を分けられない。
- → **社員アカウント制にするには、ここを作り替える必要がある。**（フェーズ0）

### 参考になる既存資産

会社の **工程表アプリ（koujitei-gantt / `kouzi-kouteihyou`）** は、すでに
Supabase Auth と社員・役割テーブル（`koujitei_users`、role = admin/member）で動いている。
認証とロール設計は、これを土台の参考・統合先にできる。

## 4. 土台の設計（フェーズ0）

全機能が乗る背骨。ここを固めてから各領域を積む。

### 4-1. 認証の入れ替え

```
現在：  QRの匿名職人／管理者PIN → Edge Function(service_role) → DB
移行後：ログイン社員（役割付き）→ RLSで役割判定 → DB
　　　　職人QR入力は従来どおり匿名のまま残す（現場で使うため）
```

- **社員**：Supabase Auth でログイン。役割は `管理者` / `担当者`。
- **職人**：現場・機械のQRから入る匿名入力は維持（アカウント不要のまま）。
- 既存の日報の書き込みも、新しい認証・権限の上に載せ替える。

### 4-2. マスタの共通化（最重要）

現場管理全般の背骨。工程表アプリと**二重管理にしない**ことが目的。

| マスタ | 内容 | 備考 |
|--------|------|------|
| 現場マスタ | 現場番号・名称・元請・担当者 | 日報と工程表で共通化する |
| 社員マスタ | 氏名・役割・ログイン | 工程表の `koujitei_users` を統合先の参考に |
| 機械マスタ | 高所作業車・重機（1台ごと・QR発行） | 新規。現場マスタと同じ作り |
| 業者マスタ | 既存 `nippo_vendors` | 現場横断で使えるよう見直し検討 |

### 4-3. 工程表アプリとの統合方針

- 工程表は現在 **別Supabaseプロジェクト**（`kouzi-kouteihyou`）で稼働。
- 「集約」＝工程表の機能をこのアプリ（`kouzi-nippo`）に取り込む方向。
- 統合の際、**現場マスタ・社員マスタを片方に寄せて一本化**する。
- ※Supabase無料枠は1組織2プロジェクトまで（現在ちょうど上限）。統合は
  プロジェクト数の整理にもつながる。実作業はフェーズ2で。

## 5. 書式テンプレート機能（フェーズ1の中核）

KY・作業員名簿・元請書式を、同じ仕組みで扱う横断機能。

### 2つの方式を使い分ける

| 書式の種類 | 方式 | 初期設定 |
|-----------|------|---------|
| 自社書式・KY | 自前でレイアウト生成（今の日報PDFと同じ jsPDF 方式） | 不要 |
| 元請の既存書式 | **元のPDFに入力値を重ね書き**（pdf-lib） | 書式ごとに1回だけ欄の位置をマッピング |

### 元請書式＝完全再現（確定）

- 提出先が指定フォーマット厳守のため、**レイアウトは元のPDFそのまま**。
- 元請書式PDFを登録 → 「この欄はPDFのどの座標か」を一度マッピング →
  以降は入力値を流し込むだけ。
- 新しい元請書式が来るたびに、この初期マッピングが1回発生する。
- 「どんなPDFでも自動で欄認識」はOCR/AI領域で精度が不安定なため採用しない。

> 次アクション：実物の元請書式PDFを数種類もらい、マッピング作業の実例を作る。

## 6. 機械・重機のQR点検記録（先行着手OK）

既存のQR＋匿名入力の仕組み（現場QR → 職人入力 → Edge Function保存）を横展開するだけ。
**4領域の中で最も早く形になる独立機能**。土台を待たずに先行着手できる。

| 要素 | 内容 | 流用元 |
|------|------|--------|
| 機械マスタ | 高所作業車・重機を1台ずつ登録・QR発行 | 現場マスタ（genba.html） |
| 点検記録 | 日常点検チェック項目＋記録・署名 | 日報（nippo_reports の保存パターン） |

> 先行着手する場合、後で土台（認証）に載せ替える手直しが少し出る点に留意。

## 7. フェーズ計画

```
先行着手OK  機械・重機のQR点検記録        独立した早い成果物
フェーズ0    土台                         社員アカウント＋役割、現場/社員/機械マスタ共通化、
                                          既存日報の認証載せ替え
フェーズ1    安全・職人管理               作業員名簿・KY・安全書類 ＋ 書式テンプレート機能
フェーズ2    工程・スケジュール           工程表アプリの集約、マスタ一本化
フェーズ3    原価・費用・発注             契約金額・発注・支払い・実行コスト
（保留）     写真・図面                   別アプリ併用で当面OK
```

規模的に数ヶ月がかりの段階的プロジェクト。**土台 → 1領域ずつ**が安全。

## 8. コスト・プランへの影響

| サービス | 現在 | 本格運用時に必要になる見込み |
|---------|------|------------------------------|
| Supabase | Free（DB 500MB / Storage 1GB / 2プロジェクトまで） | データ増・工程表統合・書類でPro検討 |
| Vercel | Hobby（**規約上 商用利用不可**） | 社員全員で本格運用するならPro |

- 署名は現在DBに直接埋め込む作り。書類・ファイルが増える前にStorage運用へ寄せる設計見直しが要る。
- 写真・図面を取り込む段階になると容量要因が一気に増える（保留が有利な理由）。

---

## 9. リスク・留意点

- **稼働中の認証切り替え**：フェーズ0で認証を入れ替える際、本番稼働中のため移行手順を慎重に。
  旧PIN運用と新アカウント運用の切替タイミングを設計する。
- **マスタ二重管理**：工程表アプリと現場・社員マスタがバラバラだと破綻する。統合方針を先に固める。
- **素のJSの限界**：機能が増えると画面間の共通化・状態管理が重くなる。土台整備のタイミングで
  共通部品の作り方（このまま素のJSで広げるか／軽量な構造を入れるか）を一度決める。
- **データ移行**：既存日報を新しいマスタ・認証モデルへ載せ替える移行作業が発生する。
